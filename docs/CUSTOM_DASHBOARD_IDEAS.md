# 自定义仪表盘 — 头脑风暴与设计草案

> 状态：🔲 待办（已列入 `KANBAN.md`）
> 目标：让用户自行拼装需要看的界面，而不是被固定的页面结构限制。
> 本文是**方案探讨**，不是最终设计；结论待确认后再进入实现。

---

## 1. 为什么要做

当前每个页面的信息密度和组合方式是写死的：

- 想知道"设备在线状态 + 当前执行到哪一步 + 某个解析值是否越界" → 要在 设备页 / 执行页 / 日志页 之间来回切
- 长稳测试（跑几小时）真正需要盯的只有 2~3 个数（循环计数、错误帧计数、电压），却被淹没在大量无关信息里
- 不同角色关注点不同：调试工程师看原始收发，产线操作员只看 PASS/FAIL 和良率

**一句话目标：把"我要看什么"的决定权交给用户。**

---

## 2. 核心概念

```
仪表盘 Dashboard  =  一组 Widget 的布局 + 各自的配置
Widget            =  一种可视化组件 + 一个数据源绑定 + 一份显示配置
数据源            =  设备 WS 流 / 执行步骤 WS 流 / 解析结果 / REST 轮询
```

一个仪表盘可以建多个（"CAN 调试"、"长稳监控"、"产线看板"），可切换、可复制。

---

## 3. Widget 清单（按优先级）

### P1 — 先做，复用现有能力

| Widget | 数据来源 | 说明 |
|---|---|---|
| 实时通信窗口 | `/ws/devices/{id}` | 直接复用已实现的终端窗口（暂停/继续/清空） |
| 执行步骤状态 | `/ws/executions/{id}` | 复用已实现的步骤窗口，含解析判定结果 |
| 设备状态卡片 | REST 轮询 | 在线/离线、协议、端口、连接时长 |
| 执行统计卡片 | REST 轮询 | 总次数/通过率/失败数/运行中 |
| 快捷执行 | REST | 选用例 → 一键执行并自动跳到本仪表盘 |

### P2 — 配合新做的"结果解析"能力，价值最大

| Widget | 说明 |
|---|---|
| **解析数值卡片** | 绑定某个用例步骤的解析字段（如"母线电压"），实时显示解析值 + PASS/FAIL 徽标，越界变红 |
| **阈值告警条** | 解析值超出 min/max 时高亮 + 可选声音/浏览器通知 |
| **趋势曲线** | 解析值随时间变化（长稳测试看漂移，最能暴露偶发问题） |
| **判定结果汇总** | 本次执行各步骤的判定表格（哪些字段 FAIL 及原因） |

> 这一组是把"能解析"变成"看得见"的关键 —— 只有解析值被持续可视化，长稳测试才有意义。

### P3 — 锦上添花

| Widget | 说明 |
|---|---|
| 通信日志表格 | 分页/过滤的收发记录 |
| 用例列表 | 直接勾选批量执行 |
| 文本/Markdown 备注 | 接线说明、操作 SOP，方便产线 |
| 自定义 iframe/图片 | 嵌入示波器截图、外部监控页 |

## 4. 交互设计

**编辑模式**
- 顶部切换"编辑 / 锁定"。锁定后不可拖动，防误触（产线场景必需）
- 从右侧组件库拖拽添加 Widget
- 拖动调整位置，拖拽右下角调整尺寸
- 每个 Widget 右上角齿轮 → 配置抽屉（数据源、字段、刷新频率、阈值、颜色）
- 删除 / 复制 Widget

**布局**
- 栅格：`react-grid-layout`（成熟、支持响应式与断点）
- 断点：桌面 12 列 / 平板 8 列 / 窄屏 4 列，同一份配置自动适配

**持久化**
- 新表 `dashboards`：`id / name / layout(JSON) / widgets(JSON) / is_default / created_at`
- Widget 配置里存"数据源引用"（device_id、testcase_id、step_index、parser 字段名），**不存具体数值** —— 数值是运行时数据，不落库

**多仪表盘**
- 顶部下拉切换；支持"复制为新建"、"设为默认"、"导出 JSON / 导入 JSON"
- 建议内置 2 个模板：**调试视图**（通信窗口 + 步骤状态 + 设备状态）、**长稳视图**（解析数值卡片 + 趋势曲线 + 告警条）

## 5. 技术方案要点

**数据总线（关键决策）**
不能让每个 Widget 各开一条 WebSocket —— 10 个 Widget 就是 10 条连接。
做法：页面级**单例 WS 订阅中心**，维护 `deviceId → 订阅者列表`、`executionId → 订阅者列表`，Widget 按需订阅、按引用计数决定何时断开。

**性能**
- 通信窗口限流渲染（如 100ms 批量 flush）+ 行数上限
- 趋势图环形缓冲（只保留最近 N 个点，如 5000）
- 页面不可见（`visibilitychange`）时暂停渲染，恢复时补最新值

**实时性 vs 开销**
- 解析数值卡片：跟随步骤 WS 事件更新（零额外请求）
- 设备状态/统计卡片：REST 轮询（5~10s），可配

## 6. 分阶段落地建议

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P1** | 栅格布局 + Widget 注册表 + 5 个基础 Widget + 持久化 CRUD + 编辑/锁定 | 能拼出"调试视图" |
| **P2** | 解析数值卡片 + 阈值告警 + 趋势曲线 + 判定汇总 | 能拼出"长稳视图"，解析能力真正被看见 |
| **P3** | 模板、导入导出、多仪表盘、产线只读模式、响应式断点 | 可交付产线使用 |

建议 **P1 与 P2 一起做**：只有基础栅格而没有数值卡片，仪表盘的吸引力有限；而解析能力刚落地，正是接上去的最好时机。

## 7. 待确认的问题

1. **是否需要多用户/权限？** 目前是单机单用户，若上产线需要"只读账号不能改布局"
2. **告警方式？** 浏览器通知 / 声音 / 写入日志 —— 产线场景倾向明显提示
3. **趋势数据是否要落库？** 若要事后复盘几小时的漂移，需要新增 `metric_points` 表（量级：1 点/秒 × 8 小时 ≈ 3 万点，SQLite 可接受）
4. **是否需要大屏模式？** 车间电视看板需要更大字号和自动轮播

---

## 8. 一句话总结

> 当前已经有了"实时通信"和"步骤状态"两块拼图，再加上刚落地的"结果解析"，
> 自定义仪表盘是把这三块按用户意愿自由组合的那块底板 ——
> 它让系统从"我给你看这些页面"变成"我盯着这几个数"。
